## 1. The operating loop (every slice runs this way)

1. **Spec** — the lead specs the slice from the work order and roadmap, with acceptance criteria written before code.
2. **Build** — Opus builder subagents implement. Builders never review their own work.
3. **Review, three ways** — an independent adversarial reviewer subagent attacks the diff; the lead reviews everything; the push to the PR triggers hosted **Codex review** on GitHub — the cross-platform brain check (two different model families reading the same diff).
4. **Field test** — Adam runs the installed plugin on real builds in his other projects (the Rooms pattern). The receipts and host-surface evidence come back to this session for evaluation. **The plugin in the field is the delivery vehicle and the test harness at once.**
5. **Gate** — a slice is done when its field gate passes, not when CI is green. This rule exists because of finding F2: the project has already been burned once by green checks that proved nothing about the runtime.

Roles, standing: *The builders produce (Opus subagents here; Codex in the field). The evaluators examine (adversarial subagents, hosted Codex review, blind readers). Lyhna witnesses (the plugin on Adam's real builds). Adam decides.*

### CZ-14 — Seal-as-you-go (checkpoint anchors)
Adam's decision (2026-07-22): checkpoint anchors over an operator-close command. A checkpoint anchor written at every Stop makes any run a verifiable packet at its last checkpoint; the receipt face states its lifecycle in observational vocabulary only (`SEALED`; close-requested-but-not-sealed with the deferred-close blockers surfaced as observations; or `OPEN` as of event N with no close request observed); open packets verify with the same hash-chain discipline seals use. Constraints: deterministic, zero new dependencies, additive schema, legacy runs read exactly as before.
**Field gate:** an open (unsealed) packet handed cold to a blind reader verifies and states its own lifecycle honestly, with no inferred completion; and with CZ-14 installed, the three (now four) stuck-open field runs become verifiable packets at their last checkpoints.

> **Build record (2026-07-22).** Code complete at `4aff37d`, v0.1.27, 81/81 tests (63 inherited + 18 new CZ-14 fixtures), validator green; PR #3. The loop ran as designed. The Opus builder shipped the spec (`5dea244`): checkpoint anchor at every Stop on both non-sealing paths, the three-shape lifecycle face, open-packet verification, the single-anchor-at-seal decision. The **independent Claude adversarial pass** (its findings written to a durable file, empirically reproduced with three attack scripts) then found the design's core defect: open-packet verification bound receipt *content* only to the mutable `checkpoint-anchor.json`, so a forged receipt verified whenever the ledger had advanced past the checkpoint (F1, P0), and a deduped `close_deferred` moved `as_of_seq` onto a non-checkpoint event, nulling the renderer gate and defeating even the at-anchor branch — precisely the B11 shape (F2, P0); plus a seal-brick regression where pre-seal checkpoint receipts made `repairSeal` false-fail an interrupted seal (F3, P1), a torn-checkpoint-write false-tamper (F4, P1), a stale-blocker honesty defect (F5, P2), and two P3s. The lead fix round (`4aff37d`) moved the trust root fully into the hash chain: every Stop appends a hash-chained `checkpoint_anchor` event committing the receipt hashes, state hash, and renderer version *before* any file is written, so no combination of file edits selects a weaker path; interrupted seals recover by recognizing checkpoint bytes through their ledger commitment; torn writes verify structurally at the prior anchor and heal at the next Stop; recurring blocker sets append fresh observations. All six new fixtures pin the findings; the reviewer's three attack scripts re-run clean. Hosted Codex round on `4aff37d`: **zero findings on the CZ-14 code**; one P2 on a handoff document (the operator's raw Windows data-root path, with the local username, committed as durable content) — fixed by scrubbing to `%USERPROFILE%` across both handoffs (`4a81708`), thread resolved. Theme, the same as Slice B and now proven twice: **the ledger is the trust root; an anchor file is a cache, and a cache must never be able to select a weaker verification path.** Running tally: eleven hosted review rounds, nine findings fixed with fixtures, none declined.

> **Process lesson (2026-07-22, recorded because the product exists to make exactly this catchable).** Between the builder finishing and the lead noticing, ~20 hours passed with nothing running: the builder's completion signal was lost to a session disconnect and the lead *waited on the signal* instead of reading the repository. The tree already held the finished work — 75/75 tests green — the whole time. A witness product's own build lead trusted a pending notification (testimony) over the working tree (the ledger). The standing correction: on any resume, the first act is to read the tree and the PR state directly, never to wait on a signal that may not arrive. It is the same failure the adapter is built to expose, and it belongs in the record.

## 3. Standing rules

- One live edge at a time; a slice ships only when the one below passed its field gate.
- The honesty ceiling is constitutional in every slice; the permission vocabulary is banned from schemas and surfaces.
- Blind at the boundary, never at the eyes: disclosure is tiered at export; capture is never impoverished to make export easier.
- Every slice's evidence (field receipts, blind reads, Codex reviews) is appended to the review record so no future session has to re-derive this.

*The builder produces. The evaluator examines. Lyhna witnesses. The corpus grades. Adam decides.*
